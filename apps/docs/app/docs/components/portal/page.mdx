# Portal

Renders its children into `document.body`, or another element, outside the parent DOM tree.

## Import

```tsx
import { Portal } from "@merid/react";
```

## Anatomy

`Portal` is a single component with no markup of its own. Dialog, AlertDialog, Drawer, Popover, Tooltip, DropdownMenu, Select and Toast already portal their content; use `Portal` directly only for your own floating layers.

## Examples

### Custom container

Pass `container` to render into a specific element instead of `document.body`.

<ComponentPreview code={portalContainerCode}>
  <PortalContainer />
</ComponentPreview>

<Callout tone="warning">
  While `container` is `null` — for example before a callback ref has run — content falls back to `document.body`, then moves once the element is set.
</Callout>

### Server rendering

`Portal` renders nothing on the server and during hydration, then mounts on the client. Don't put content in a portal that must be in the initial HTML.

## Styling

`Portal` adds no classes, attributes or CSS variables. Content inside it is still in the React tree (context and events bubble through React), but CSS inherits from the target element, so portalled content is outside any ancestor `overflow`, `transform` or stacking context.

## Accessibility

Portal is a utility, not a widget, so there is no APG pattern. It changes DOM order, which is also reading and `Tab` order: when portalled content is interactive, manage focus yourself as the [APG dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) describes, or use one of Merid's overlay components, which already do.

Portal has no keyboard interactions of its own.
